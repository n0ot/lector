# tmux input, focus, mouse, paste, and sizing

Lector never places application bytes directly in tmux command syntax. Each
adjacent input batch is assigned to the pane that is active when the complete
terminal input event is decoded, split into commands no larger than 4096 bytes,
and sent as one two-digit hexadecimal argument per byte:

```text
send-keys -H -t %21 00 1b 5b 31 32 30 3b 35 3a 31 75
```

This representation is binary-safe for NUL, invalid UTF-8, newlines, quotes,
semicolons, tmux format markers, and every other byte. Adjacent key events are
coalesced until another control command changes their ordering boundary. The
event loop requests an immediate tick whenever a batch is pending, so batching
does not add a timer delay.

All inventory, capture, resync, input, flow-control, and size commands share
one FIFO. Expected reply types are registered only after the corresponding
command has been written successfully. Replies to `send-keys`,
`refresh-client`, and flow-control commands are consumed explicitly and cannot
be mistaken for a later inventory or bootstrap reply.

## Paste and terminal replies

Bracketed-paste delimiters are semantic. Lector parses the outer paste event,
checks the active pane's own Ghostty mode, and adds `CSI 200 ~` and `CSI 201 ~`
only when that pane requested bracketed paste. The resulting bytes use the same
hexadecimal, bounded command path as keyboard input, so large or adversarial
pastes require no shell or tmux quoting.

Terminal query replies generated by a pane's Ghostty engine are returned to
that same pane through the input FIFO. Replies from hidden panes retain their
source identity; they are not redirected to whichever pane later becomes
active.

## Focus and mouse

Outer focus events update Lector's accessibility focus state. They are sent to
tmux only when the currently active pane requested focus reporting.

Mouse events are accepted only for the active pane and only when their scene
coordinates lie inside that pane rather than on a border or another pane. The
coordinates are translated to pane-local zero-based positions, then re-encoded
as the pane's requested default, UTF-8, or SGR mouse format. Press, release,
button-motion, and any-motion events are gated independently by the pane's
current Ghostty mouse protocol. Rejected tmux mouse events are dropped instead
of being forwarded with incorrect scene coordinates.

Lector's review-cursor click actions already produce pane-local coordinates
from the active pane model. They enter the same binary-safe input queue.

## Size and flow control

An outer resize changes the physical scene immediately but does not directly
resize a tmux pane engine. Lector coalesces resize storms to the newest:

```text
refresh-client -C 120x40
```

Pane engines change size only after tmux supplies authoritative layout and
pane geometry. The size update still reaches the control client while a Lector
review overlay or portal is visible.

At connection startup Lector requests `pause-after=1`. When tmux reports
`%pause %N`, Lector queues exactly one `refresh-client -A %N:continue` in the
ordered control FIFO even if pause notifications repeat. `%continue` clears
the pane's paused state. Stale `%extended-output` is not guessed into the pane
engine: it starts an authoritative text/history capture while further bytes in
that lost interval are coalesced. The complete policy, recovery guarantees, and
media/parser limitations are documented in
[`tmux-completion.md`](tmux-completion.md).

## Regression harnesses

`tests/tmux_input.rs` covers all 256 byte values, invalid UTF-8, malicious
command-shaped input, every supported mouse encoding and protocol gate,
coordinate translation, keyboard protocol preservation, large paste chunking,
query ownership, partial input during active-pane changes, reply correlation,
resize storms, overlay resize, and explicit `%pause` recovery.

Its non-ignored real tmux 3.7b harness starts an isolated server and a raw
byte-echo child. Lector drives NUL, control, UTF-8, invalid UTF-8, legacy Meta,
Kitty keyboard, focus, mouse, bracketed paste, rapid resize, and a 128 KiB
output flood through the actual control client. The child renders each received
byte as hexadecimal, providing an independent end-to-end input oracle without
timing sleeps. The release latency check queues and encodes 10,000 adjacent
bytes under a deliberately generous regression budget.
