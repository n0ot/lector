# tmux input, focus, mouse, paste, and sizing

Lector never places application bytes directly in tmux command syntax. Each
adjacent input batch is assigned to the pane that is active when the complete
terminal input event is decoded, split into commands no larger than 4096 bytes,
and sent as one two-digit hexadecimal argument per byte:

```text
send-keys -H -t %21 00 1b 5b 31 32 30 3b 35 3a 31 75
```

This representation is binary-safe for NUL, invalid UTF-8, newlines, quotes,
semicolons, tmux format markers, and every other byte. Adjacent key events are
coalesced until another control command changes their ordering boundary. The
event loop requests an immediate tick whenever a batch is pending, so batching
does not add a timer delay.

All inventory, capture, resync, input, flow-control, and size commands share
one FIFO. Expected reply types are registered only after the corresponding
command has been written successfully. Replies to `send-keys`,
`refresh-client`, and flow-control commands are consumed explicitly and cannot
be mistaken for a later inventory or bootstrap reply.

## Paste and terminal-query ownership

Bracketed-paste delimiters are semantic. Lector parses the outer paste event,
checks the active pane's own Ghostty mode, and adds `CSI 200 ~` and `CSI 201 ~`
only when that pane requested bracketed paste. The resulting bytes use the same
hexadecimal, bounded command path as keyboard input, so large or adversarial
pastes require no shell or tmux quoting.

Lector owns the root child PTY and returns that engine's terminal-query replies
directly to the child. It does not own a pane PTY observed through tmux control
mode. Most replies generated by pane Ghostty engines are therefore discarded;
injecting them with `send-keys` would turn a terminal report into application
input. OSC 10 and OSC 11 default-color queries are the documented exception:
tmux forwards those queries to control clients, so Lector returns the raw
pane-scoped report with `refresh-client -r '%N:<report>'`. If a pane asks
during startup, that report waits behind its transport's ordering boundary
until Lector has either learned the outer terminal's exact defaults or reached
the bounded probe deadline; the reported colors are then reconciled with the
same profile used for direct children.

Physical-terminal startup probes have the same durable ownership rule. The
inactivity deadline makes ordinary keyboard input ready, but delayed responses
to Lector's earlier physical queries remain Lector-owned until the final DA1
response arrives. That ordered response is a processing fence: after consuming
it, the startup broker passes every subsequent byte through without classifying
escape prefixes. Application queries are answered by the root virtual engine
and are never emitted to the physical terminal. Thus slow or backpressured
physical replies cannot later appear as keys in a full-screen application such
as Codex, while post-fence Meta keys do not pay the probe timeout.

## Focus and mouse

Outer focus events update Lector's accessibility focus state. They are sent to
tmux only when the currently active pane requested focus reporting.

Mouse events are accepted only for the active pane and only when their scene
coordinates lie inside that pane rather than on a border or another pane. The
coordinates are translated to pane-local zero-based positions, then re-encoded
as the pane's requested default, UTF-8, or SGR mouse format. Press, release,
button-motion, and any-motion events are gated independently by the pane's
current Ghostty mouse protocol. Rejected tmux mouse events are dropped instead
of being forwarded with incorrect scene coordinates.

Lector's review-cursor click actions already produce pane-local coordinates
from the active pane model. They enter the same binary-safe input queue.

## Size and flow control

An outer resize changes the physical scene immediately but does not directly
resize a tmux pane engine. Lector coalesces resize storms to the newest:

```text
refresh-client -C 120x40
```

Pane engines change size only after tmux supplies authoritative layout and
pane geometry. The size update still reaches the control client while a Lector
Review overlay or portal is visible. An open Review layer separately retains
its frozen document and creates a viewport for the new geometry. It preserves
the cursor's screen row and column where possible, fills newly available space
with surrounding content at document boundaries, pans horizontally when
needed, and immediately uses the new height for page motions. Closing Review
therefore reveals a tmux view that has already adopted tmux's authoritative
post-resize layout.

At connection startup Lector requests `pause-after=1`. tmux discards pane
output while a control client is paused, so `%pause %N` also marks Lector's
pane model stale. When the pane is visible, Lector queues exactly one
`refresh-client -A '%N:continue'` in the ordered control FIFO even if pause
notifications repeat, then rebuilds the pane from `capture-pane`. `%continue`
clears the transport's paused state, as does the successful reply to the
explicit resume command (tmux may place `%continue %N` inside that command's
output block). If output keeps racing ordinary recovery until its hard deadline,
Lector pauses again and sends the final `continue` and capture as one parsed
tmux command sequence, making the snapshot the boundary at which incremental
delivery restarts.
The age in `%extended-output` is delivery telemetry, not evidence of dropped
bytes, so even old records remain ordinary incremental output. `%pause` is the
loss boundary that starts an authoritative capture while further bytes in that
interval are coalesced. The complete policy, recovery guarantees, and
media/parser limitations are documented in
[`tmux-completion.md`](tmux-completion.md).

## Regression harnesses

`tests/tmux_input.rs` covers all 256 byte values, invalid UTF-8, malicious
command-shaped input, every supported mouse encoding and protocol gate,
coordinate translation, keyboard protocol preservation, large paste chunking,
query ownership, partial input during active-pane changes, reply correlation,
resize storms, overlay resize, and explicit `%pause` recovery.

Its Docker-only real-tmux harness starts an isolated server and a raw
byte-echo child. Lector drives NUL, control, UTF-8, invalid UTF-8, legacy Meta,
Kitty keyboard, focus, mouse, bracketed paste, rapid resize, and a 128 KiB
output flood through the actual control client. The child renders each received
byte as hexadecimal, providing an independent end-to-end input oracle without
timing sleeps. The harness is ignored by ordinary Cargo runs and selected by
`scripts/test-real-tmux-docker`. The release latency check queues and encodes
10,000 adjacent bytes under a deliberately generous regression budget.
